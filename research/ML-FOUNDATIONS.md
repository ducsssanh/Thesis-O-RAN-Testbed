# Machine-Learning Foundations of the Cross-Domain Defence

Status: 2026-10-25. Companion of `research/CROSS-DOMAIN-DEFENCE.md` (system and results). This document explains
the ML part from first principles: the learning problem, the features, the model (gradient-boosted decision trees),
how its output becomes a decision, how it was evaluated, why this model was chosen over the alternatives, and why
the xApp serves it the way it does. The design of the decision pipeline around the models (integrity check, trust,
escalation) is justified in `CROSS-DOMAIN-DEFENCE.md` §4.4.

**Short answer to "which GBDT framework?"** — not XGBoost. The three models are scikit-learn
`sklearn.ensemble.HistGradientBoostingClassifier` (scikit-learn 1.9.1, serialised with joblib 1.6.0, numpy 2.5.4),
the histogram-based gradient boosting algorithm of LightGBM re-implemented in scikit-learn. XGBoost, LightGBM and
this estimator belong to the same family (second-order gradient boosting of regression trees); §6 explains the choice.

---

## 1. The learning problem

For every UE $u$ and every second $t$ the defence must output a score that the UE is **flooding** (malicious) rather
than sending **legitimate high load** (benign) of the same volume.

- **Sample**: one window end $(u, t)$ with the telemetry of the past 30 s.
- **Label** $y \in \{0, 1\}$: the label of the last second (MALICIOUS = 1, BENIGN = 0). IDLE seconds (no flow) are never
  a training target; an activity gate (§4.3) keeps them out of the decision.
- **Training set** (v4 dataset, 88 runs, split by run, seed 20261023): only *main* windows — all seconds inside one
  phase with one label, away from the 3 s phase boundaries — so a window never mixes the previous phase. Train:
  29,762 windows (13,878 malicious) from 56 runs; validation 7,494 windows (3,704) from 14 runs; test 9,016 windows
  (4,281) from 18 runs.
  The ICMP negative-control pair is excluded from training (it is a control, not a target).
- **Why split by run, not by row**: consecutive seconds of one run are strongly correlated; a row split would put
  near-identical windows in train and test and inflate every metric (leakage found and removed in the earlier datasets).

The task is deliberately hard: benign traffic is **load-matched** (same rate as the flood), so volume alone cannot
separate the classes; the models must use shape, protocol mix, packet-size and cross-domain consistency.

## 2. Features

### 2.1 Raw telemetry (31 columns, UL subset used: 17)
| domain | columns (per UE per second) |
|---|---|
| RAN (E2SM-KPM) | UL/DL rate, UL/DL throughput, UL/DL PRB %, cell UL/DL PRB % |
| core (PFCP URR) | UL/DL kbit/s, UL/DL packets/s (rate = volume ÷ report period, from consecutive cumulative reports) |
| core (eBPF profiler in the UPF) | UL/DL kbit/s and pps, mean packet size, counts of TCP, TCP-SYN, UDP, ICMP, fragments, DNS, GTP-in-GTP, destination-count estimate |

The detector is **UL-only** (DL features are excluded): in the testbed the benign DL is generated by the experiment
itself, so DL would make the problem trivially separable (ROC-AUC 0.995) for a reason that does not exist in a real
network. A leak check confirms that RAN UL ratios carry no indirect DL label information.

### 2.2 Transformation
- magnitudes (rates, counts): $x \mapsto \log(1 + \max(x, 0))$ — compresses the heavy-tailed range (0 to tens of
  Mbit/s) so that a factor change has a similar effect at every scale;
- percentages: $x / 100$;
- missing values (URR or profiler older than 4 s, KPM older than 3 s) stay **NaN** for the trees (handled natively,
  §3.5). (The LSTM baseline additionally z-scores and maps NaN → 0.)

### 2.3 Causal rolling statistics
For each transformed column $x$ and each window $w \in \{5, 10, 30\}$ s, over the past $w$ seconds of the same UE
(at least 2 points, never using the future):

$$\bar x_w=\frac{1}{n}\sum_{i} x_i,\qquad
s_w=\sqrt{\frac{1}{n}\sum_i (x_i-\bar x_w)^2},\qquad
\max_w = \max_i x_i,\qquad
\beta_w=\frac{\overline{t x}-\bar t\,\bar x}{\overline{t^2}-\bar t^{\,2}}$$

where $\beta_w$ is the least-squares slope of $x$ against time (trend: ramping vs steady traffic). Each column thus
yields 13 features: the 1 s value + 3 windows × {mean, std, slope, max}.

| model | raw UL columns | features |
|---|---|---|
| RAN-only | 4 KPM UL columns | 4 × 13 = 52 |
| core-only | 13 URR + profiler UL columns | 13 × 13 = 169 |
| cross-domain | all 17 UL columns | 17 × 13 = 221 |

**Why rolling statistics instead of a sequence model**: floods differ from load-matched benign traffic in
*variability* (std), *trend* (slope), *burstiness* (max vs mean) and *protocol mix* over seconds to tens of seconds.
Making these explicit lets a tabular model use history without learning the aggregation itself; offline, 30 s of
history beat 10 s (+0.030 ROC-AUC) and 1 s (0.790).

**Exactness offline ↔ live**: the live sidecar recomputes these features per step with the *same code*
(`prep_v4_windows.transform` + `rolling` inside `defence_engine_v4.OnlineFeatures`); a parity test showed live
features equal to the offline ones within 1e-6 and identical decisions on recorded runs.

## 3. Gradient-boosted decision trees

### 3.1 Decision trees
A regression tree partitions the feature space into axis-aligned regions (leaves) by threshold tests
$x_j \le c$ and outputs a constant $w_\ell$ in each leaf $\ell$. Trees capture thresholds and interactions
("high UDP share **and** low packet-size variance") without feature scaling and are insensitive to monotone
transformations of a feature.

### 3.2 Additive model and loss
Boosting builds an additive model of $M$ trees in log-odds space:

$$F_M(\mathbf x)=F_0+\eta\sum_{m=1}^{M} f_m(\mathbf x),\qquad
p(\mathbf x)=\sigma\!\big(F_M(\mathbf x)\big)=\frac{1}{1+e^{-F_M(\mathbf x)}}$$

trained to minimise the binary cross-entropy (log loss)

$$\mathcal L=\sum_{i}\ell(y_i,F(\mathbf x_i)),\qquad
\ell(y,F)=-\big[y\log\sigma(F)+(1-y)\log(1-\sigma(F))\big].$$

$F_0$ is the log-odds of the training prior; $\eta$ is the learning rate (shrinkage).

### 3.3 Second-order (Newton) boosting step
At iteration $m$ each sample has gradient and Hessian of the loss at the current prediction:

$$g_i=\frac{\partial \ell}{\partial F}=p_i-y_i,\qquad h_i=\frac{\partial^2 \ell}{\partial F^2}=p_i(1-p_i).$$

A second-order Taylor expansion of the loss with an L2 penalty $\lambda$ on the leaf values gives, for a leaf with
sample set $I$, the optimal value and the loss reduction it brings:

$$w^\ast=-\frac{G}{H+\lambda},\qquad \text{score}(I)=\frac{G^2}{H+\lambda},\qquad G=\sum_{i\in I}g_i,\; H=\sum_{i\in I}h_i.$$

A split of $I$ into $I_L, I_R$ is chosen to maximise the gain

$$\text{Gain}=\tfrac12\left[\frac{G_L^2}{H_L+\lambda}+\frac{G_R^2}{H_R+\lambda}-\frac{G^2}{H+\lambda}\right].$$

This is the same objective as XGBoost and LightGBM; the frameworks differ in how they search splits and grow trees.

### 3.4 Histogram-based split search and leaf-wise growth
- Every feature is binned once into at most 255 quantile bins (`max_bins=255`); split search then sums $g, h$ per
  bin instead of sorting samples — $O(\text{bins})$ per feature and node, which makes training on ~30 k × 221
  features take seconds.
- Trees grow **leaf-wise** (best-gain leaf first) up to `max_leaf_nodes=31`, with `min_samples_leaf=20`
  (regularises leaves on few samples); no depth limit.

### 3.5 Missing values
At each split the samples with a missing value are tried on both sides and sent to the side with the larger gain;
the learned direction is stored per node. Stale core telemetry (core outage) or stale KPM therefore needs no
imputation, and the model learns what "missing" means from the training data (URR missing on 0.3–0.7 % of benign /
malicious rows, 6 % of idle rows).

### 3.6 Hyper-parameters (frozen in `artifacts/ml/v4/models/`)
| parameter | value | role |
|---|---|---|
| `loss` | log_loss | binary cross-entropy |
| `learning_rate` η | 0.1 | shrinkage per tree |
| `max_iter` | 300 | number of boosting iterations (all three models used 300) |
| `max_leaf_nodes` / `min_samples_leaf` | 31 / 20 | tree complexity |
| `l2_regularization` λ | 0 | (leaf L2) |
| `max_bins` | 255 | histogram resolution |
| `early_stopping` | auto (on: > 10 k samples), 10 % internal validation, patience 10 | did not trigger before 300 |
| `random_state` | 0 | reproducibility |
Library defaults except `max_iter`; no hyper-parameter search was run (a deliberate choice: the comparison of
feature sets and of GBDT vs LSTM must not be confounded by unequal tuning effort; tuning is listed as future work).

## 4. From probability to decision

### 4.1 Operating point
Each model's threshold $\theta$ is set on the **validation runs** so that at most **1 % of benign windows** (with the
activity gate) score above it: $\theta_{\text{xd}}=0.9732$, $\theta_{\text{core}}=0.9676$, $\theta_{\text{ran}}=0.9641$.
Thresholds are high because the classes overlap and the cost of a false alarm (isolating a legitimate user) is high.

### 4.2 Normalised score
$z = p/\theta$ puts the three models on one scale ($z \ge 1$ ⇔ that model's alarm at its own 1 % FPR operating
point), which makes the trust-weighted combination $z_{\text{fused}}$ meaningful (`CROSS-DOMAIN-DEFENCE.md` §4.1).

### 4.3 Activity gate and temporal smoothing
- Gate: a UE is scored only if its 10 s mean UL ≥ 50 kbit/s (core view if fresh, else RAN view) — an idle UE cannot
  be an attacker and would otherwise produce false alarms from noise.
- k-of-n: an alarm counts only when $z_{\text{fused}} \ge 1$ in **3 of the last 5 seconds**. Offline (cross-domain model,
  honest telemetry) this trades a little recall for far fewer false alarms:

| rule | attack phases detected | median time (s) | benign phases with any alarm |
|---|---|---|---|
| 1 of 1 | 0.80 | 13.2 | 0.117 |
| 2 of 3 | 0.76 | 14.3 | 0.087 |
| **3 of 5** | 0.70 | 15.2 | **0.039** |
| 5 of 5 | 0.64 | 17.3 | 0.029 |

3 of 5 was chosen as the knee: false alarms fall 3× from 1-of-1, further strictness buys little.

## 5. Evaluation methodology
- **Threshold-free**: ROC-AUC (probability that a random malicious window outranks a random benign one), PR-AUC.
- **At the operating point**: TPR at the frozen 1 % FPR threshold; per-phase detection rate and time-to-detect.
- **Uncertainty**: bootstrap over **runs** (resampling whole runs, not windows, respects within-run correlation),
  95 % percentile intervals; model comparisons use a **paired** bootstrap (both models scored on the same resampled
  runs, the CI of the difference).
- **Leakage controls**: run-level split; main windows only; previous-phase label not exploited (cutting history at
  the phase start does not lower the score); indirect-DL check; negative control (ICMP flood vs ping ≈ chance for
  every model using core data).
- **Robustness transfers**: across UEs (0.87–0.91), across victim responses (0.80–0.94), to an unseen traffic
  generator (0.64–0.79 — the main weakness).

Offline results (`research/datasets/oran_flooding_v4/reports/model_eval_v4.md`): cross-domain GBDT ROC-AUC 0.930
[0.894, 0.961], PR-AUC 0.924, TPR at 1 % FPR 0.467; core-only 0.908; RAN-only 0.865.

## 6. Why GBDT — and why this implementation

### 6.1 GBDT vs the LSTM (measured, not assumed)
The thesis plan originally named an LSTM (2 layers × 64 units, 10 s sequences of the z-scored raw features):

$$\mathbf i_t=\sigma(W_i\mathbf x_t+U_i\mathbf h_{t-1}+\mathbf b_i),\;
\mathbf f_t=\sigma(\cdot),\; \mathbf o_t=\sigma(\cdot),\;
\tilde{\mathbf c}_t=\tanh(\cdot),\;
\mathbf c_t=\mathbf f_t\odot\mathbf c_{t-1}+\mathbf i_t\odot\tilde{\mathbf c}_t,\;
\mathbf h_t=\mathbf o_t\odot\tanh(\mathbf c_t)$$

with a sigmoid head on $\mathbf h_T$, trained with Adam (lr 1e-3, dropout 0.2, 40 epochs). On v4 it was worse than a
GBDT given the **same 10 s history** by −0.067 ROC-AUC [−0.093, −0.041] (paired bootstrap), lost more from validation
to test (−0.074 vs −0.029: it fits run-specific patterns), was nearly order-blind (shuffling the 10 steps cost 0.010
AUC) and failed on the CBR UDP pairs (0.65–0.66 vs 0.78–0.90). With ~30 k training windows from 56 runs there is not
enough data for the sequence model to learn the aggregations that the rolling features give the GBDT for free.

### 6.2 GBDT properties that fit this problem
| need | GBDT property |
|---|---|
| tabular, heterogeneous, heavy-tailed features | invariant to monotone transforms, no scaling needed |
| missing core telemetry is normal (outage, staleness) | native missing-value routing (§3.5) |
| interactions (protocol mix × variability × volume) | trees model interactions directly |
| small dataset (tens of thousands of correlated windows) | strong defaults, little tuning, robust across run splits (0.932 ± 0.012 over 3 splits) |
| 1 s control loop with a 200 ms budget | prediction = 300 tree look-ups per model; whole step (features + 3 models + rules) p50 19.5 ms, p99 47.9 ms |
| explainability for a thesis | feature-importance / per-split inspection possible; decisions are deterministic |

### 6.3 Why scikit-learn's HistGradientBoosting rather than XGBoost / LightGBM
- **Same algorithm family**: second-order boosting with histogram split search and leaf-wise growth — LightGBM's
  algorithm, which XGBoost's `hist` method also implements. On a problem of this size the three are expected to
  perform within noise of each other; this was **not measured** here (no head-to-head run), and the thesis should say
  so rather than claim superiority of the library.
- **One dependency stack**: the whole pipeline (dataset builder, baselines, evaluation, the live sidecar) already uses
  scikit-learn / numpy / pandas; the sidecar image pins the exact scikit-learn version of training, so a model file
  trained offline loads bit-identically live (sha256 of every model recorded in the pre-registration).
- **Determinism and parity**: the offline replay and the live sidecar call the same Python engine; one library and
  one serialisation format keep the 1e-6 feature parity and identical decisions.
- **Adequate speed**: training of the three models takes seconds; inference fits the loop budget (§6.2), so the
  extra speed of a C++ library is not needed.

## 7. Why the xApp is built as "C xApp + Python model sidecar"

| decision | reason | alternative considered |
|---|---|---|
| **The xApp (C, FlexRIC SDK) is the single decision point** for both domains | O-RAN places near-RT control in the RIC; the author's design keeps the UPF a sensor / enforcer with per-UE memory, not a second brain; one place sees both domains at once, which the integrity check needs | a decision service in the core (rejected: two brains, unclear authority) |
| **ML runs in a sidecar container** in the xApp pod, called over loopback HTTP (`POST 127.0.0.1:8091/classify`) | the ML ecosystem is Python; the same engine module serves the offline replay and the live system (exact parity); the model can be swapped or its mode changed at run time without rebuilding the C xApp | ONNX/treelite inference compiled into the C xApp (faster, but a second implementation of the features and decisions to keep identical); a separate RIC-platform service (network hop, more failure modes) |
| **Loopback, same pod** | no network between xApp and model; measured p50 19.5 ms / p99 47.9 ms per call | — |
| **Hard timeout 200 ms + rule fallback** | the xApp's 1 s loop must never stall on the model; if the sidecar is slow or down, the fair-use rules decide that step and the event is counted (34 of 124,758 calls) | blocking call without timeout (a stuck model would stop the defence) |
| **Stateful sidecar, one step per new KPM report** | rolling features need per-UE history; stepping only on a new KPM sequence number means a KPM stall pauses the logic instead of feeding stale data (measured KPM age at every step ≤ 0.09 s) | stateless model fed the whole window by the xApp (larger requests, history logic duplicated in C) |
| **Escalation timing and actuation stay in C** | actuation (E2SM-RC, UPF API, TTLs, expiry, verification) existed and was validated before the ML stage; the sidecar returns a label, a score and which domain(s) support it, the xApp's policy turns that into actions | moving the whole policy into Python (re-validating every actuator) |
| **Core telemetry via A1-EI** | standard O-RAN enrichment-information path from the Non-RT RIC; no non-standard core→RIC interface | direct UPF→xApp feed (faster, but non-standard) |
| **Runtime REST API on the xApp** (timing, classifier, tamper, reset) | experiments change configuration per run without restarts; every setting is logged with the run | rebuild / restart per configuration |

## 8. Limitations of the ML part
- Weak transfer to an unseen traffic generator (0.64–0.79): the model partly learns tool fingerprints.
- The operating point is modest (≈47 % of attack windows at 1 % FPR); the k-of-n rule, the integrity check and the
  two-domain block rule compensate at the decision level, they do not make the classifier stronger.
- ICMP flood vs ping at the same rate is not separable with these features.
- No hyper-parameter tuning and no comparison with XGBoost / LightGBM; probabilities are not calibrated (only the
  ranking and the validation threshold are used).
- Trained on 2 UEs, one cell, RF simulator; the feature distribution of a real network will differ.
